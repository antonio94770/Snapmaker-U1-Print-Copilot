# Verified facts

What Snapmaker Orca and the Snapmaker U1 actually do, as checked on real
installations and hardware. Code comments cite the sections below. Anything
not verified is marked `TO VERIFY ON HARDWARE` or `TO VERIFY IN SNAPMAKER ORCA`.

## 1. Installation layout (Windows 11)

- Snapmaker Orca installs to `C:\Program Files\Snapmaker_Orca\`
  (`snapmaker-orca.exe` is a thin launcher; logic in `Snapmaker_Orca.dll`).
  Checked on 01.10.01.50 and 2.4.1.
- User data: `%APPDATA%\Snapmaker_Orca\`
  - `Snapmaker_Orca.conf`: app config, recent preset selections per printer
    (machine, process, filaments `filament_01..`, colours,
    `flush_volumes_matrix`, `curr_bed_type`). Structure in section 3.
  - `system\Snapmaker\{machine,process,filament}\*.json`: system presets with
    `inherits` chains. U1 machines: `Snapmaker U1 (0.2|0.4|0.6|0.8 nozzle)`.
    On 2.4.1 this folder can be missing; the bundled profiles are then in
    `resources\profiles\` under the install (section 4).
  - Presets are identified by their **`name` field, not the file name** (for
    example `Generic PLA` for the U1 0.4 nozzle lives in a differently named
    file).
  - `system\OrcaFilamentLibrary\filament\` has subfolders (`base\`, one per
    vendor); Snapmaker filaments inherit from bases there (e.g.
    `fdm_filament_pla`), so the preset scan is recursive.
  - Logs: `%APPDATA%\Snapmaker_Orca\log\`.
- U1 firmware 2.0.0 (`software_version` 2.0.0.205) for everything in
  section 5.

## 2. Snapmaker Orca CLI on 01.10.01.50 (2.4.1 updates in section 4)

Probe files are in `research/cli-probe/` (`flatten.py`, `bisect.py`, `cube.stl`
= 20 mm cube).

Working command (exit code 0, writes `plate_1.gcode`):

```
snapmaker-orca.exe --slice 0
  --load-settings "C:/…/machine_flat.json;C:/…/process_flat.json"
  --load-filaments "C:/…/fil.json;C:/…/fil.json;C:/…/fil.json;C:/…/fil.json"
  --outputdir "C:/…/out" "C:/…/model.stl"
```

Result with `0.20mm Standard @Snapmaker U1 (0.4 nozzle)` + 4× Generic PLA:
`estimated printing time (normal mode) = 15m 1s`, `total filament used [g] = 3.65`,
`layer_height = 0.2`, `wall_loops = 2`, `sparse_infill_density = 15%`,
`printer_model = Snapmaker U1`, `nozzle_diameter = 0.4,0.4,0.4,0.4`.

Gotchas found (all on 01.10.01.50):

1. The initial redirected-output probe captured no useful `--help` text.
   **Correction on 2.4.1 (2026-10-29):** help prints in a real Windows console.
   Its console attachment reopens streams on `CONOUT$`, bypassing our capture.
   The old result does not establish missing help on the earlier release.
2. **Paths must be Windows-style.** `/c/...` → "can not find setting file".
3. **Passing the bundled presets directly crashes the CLI.** Working copies
   flatten the inheritance chain and remove the process key in item 5.
   The direct-preset result does not isolate inheritance as a separate bug;
   the inherited process also contains the crashing key.
4. Flattened copies with `"from": "User"` and no `inherits` were refused as
   incompatible. **Correction on 2.4.1 (2026-10-29):** keeping `from=User` and
   restoring `inherits="Snapmaker U1 (0.4 nozzle)"` succeeds. The CLI uses the
   inherited system identity for compatibility checks; `from=system` is the
   current workaround in this project, not a universal CLI requirement.
5. **`wipe_tower_filament = "0"` in the U1 process preset segfaults the CLI.**
   Found by key bisection (`bisect.py`). Removing the key fixes it. Probably a
   Snapmaker Orca bug.
   Impact of removing it on multi-colour prints is **not verified**.
6. **`--export-3mf` segfaults** (log shows
   `PartPlate::calc_exclude_triangles: Unable to create exclude triangles` and
   `can not find key Snapmaker U1`). Slicing to G-code alone is fine. Print Copilot
   writes the `.3mf` project itself (zip with the model + `Metadata/*.config`).
7. Pass one filament per tool head (4) to match `nozzle_diameter` count; tested
   only with the same filament ×4.

Slicing and G-code:

- The G-code says `; generated by Snapmaker Orca 2.4.0` although the app is
  01.10.01.50 (2.4.0 is the internal Orca version; `Snapmaker_Orca.conf` also
  has `"header": "Snapmaker Orca 2.4.0"`).
- A cube slice takes about **0.5 s**. The CLI exits 0 and still logs harmless
  `[error] calc_exclude_triangles` lines.
- The per-tool summary (`; filament used [g] = …`, estimated time) follows
  `; EXECUTABLE_BLOCK_END`; the full config sits between `; CONFIG_BLOCK_START`
  and `; CONFIG_BLOCK_END`.
- Preset JSON stores every value as a string (`"15%"`, booleans as `"0"`/`"1"`)
  or as a list of strings for per-extruder / per-filament values
  (`"nozzle_temperature": ["220"]`). No preset key contains a dot.

Overrides, supports and toolpaths:

- **Unknown enum values can be substituted with exit code 0.**
  `support_type = bogus` becomes `normal(auto)`. The 2.4.1 audit confirmed an
  info-level message with `--debug 4`; the original no-diagnostic claim was
  incorrect. `slice_model` compares overrides with the G-code config block
  and fails if a requested value was not applied.
- `support_type` values `normal(auto)` and `tree(auto)` both work and show up
  in the config block; `enable_support = 0` gives no `;TYPE:Support` lines.
- **Measured output path limit:** a 229-character `--outputdir` works and
  230 fails in the tested Windows environment with the generated filename:
  "GCode processor post process export failed. Cannot open file for writing."
  This is not a universal directory-length limit or a verified root cause.
  `slice_model` currently uses the measured bound as a conservative check.
- The CLI centres the model on the plate by itself (model at X/Y 0..30 →
  toolpath around X/Y 135); the rotated STL is still written centred with its
  lowest point at Z 0.
- The body marks features with `;TYPE:<name>` (`Outer wall`, `Inner wall`,
  `Sparse infill`, `Support`, `Support interface`, `Bridge`, `Overhang wall`,
  `Custom`, ...), uses `M83` relative E, and retractions are E-only moves. The
  sum of positive E on X/Y moves equals the header `filament used [mm]`
  exactly (1282.89 mm on the T part with tree supports).
- T part (`tests/fixtures/tee.stl`, 30×15×25 mm, cap overhangs 300 mm²),
  0.20mm Standard, Generic PLA: as loaded, no support 2.86 g; normal 5.06 g /
  19m 53s; tree 3.83 g / 20m 41s (0.97 g support); lying on its side 2.83 g /
  11m 41s, no support needed.

3MF projects and multi-colour (all on 01.10.01.50; probes in
`research/m4-probe/`, sources read from github.com/Snapmaker/OrcaSlicer at tag
v2.4.0):

- **Every 3MF project crashes the CLI or is refused.** With `Application`
  metadata `BambuStudio-*` / `Snapmaker_Orca-*` the loader takes the project
  path and segfaults (or refuses a newer file: "Version Check: File Version
  2.2.0.1 not supported"; `--allow-newer-file` is a flag without value). A
  `<plate>` section in `model_settings.config` also segfaults: in
  `PartPlate::get_extruders_under_cli`, `expand_plate_extruders` calls
  `wxGetApp().filaments_cnt()` without a GUI app. The v2.4.1 source (released
  2026-10-28) guards exactly this ("CLI mode: no wx app / preset bundle
  exists"). Not verified on 2.4.1: the portable zip was downloaded (sha256
  matches GitHub) but running a downloaded executable was blocked in the
  agent sandbox.
- **Workaround that works:** a copy without `Application`, without plates and
  assemble sections and without `project_settings.config` (which makes the CLI
  merge the Bambu presets: "Param values in 3mf/config error"). The loader
  still reads object and part `extruder` metadata and `paint_color`. Config
  `<object id>` = build item object id; `<part id>` = component object id;
  metadata for ids that match nothing is ignored.
- `--arrange 0` keeps the build positions; by default the CLI re-arranges.
  Multiple STL inputs are always arranged. `--load-filament-ids 1,3` assigns
  one filament per input file (1-based), not per object.
- **Painting needs `filament_colour` in the filament presets.** The flattened
  presets have none, so the print config keeps one colour and
  `multi_material_segmentation_by_painting` drops every state above 1
  ("dropping painted states above segmentation range ... physical_filaments=1").
- **The purge matrix has no effect on the U1.** `flush_volumes_matrix` all 280
  or 0/500/50 with multiplier 1 gives identical numbers (two objects on T0/T2:
  7.31 + 6.86 g, 1h 58m 55s, 249 changes). `single_extruder_multi_material =
  0`. Purge per change is about 8 mm of filament inside `; CP TOOLCHANGE WIPE`
  blocks; `prime_volume` 18 -> 5 cut that run from 14.17 g to 9.35 g. Without
  the prime tower: 6.56 g and 1h 14m 21s, same 249 changes, and the header
  then has no `total filament change` line.
- `wipe_tower_filament`: removing it is harmless, the config block still shows
  `wipe_tower_filament = 0` (the default).
- G-code: tool selection is a bare `T<n>`; after it the change G-code calls
  `SM_PRINT_PREEXTRUDE_FILAMENT INDEX=<n>` (its extrusion is not in the
  G-code). On firmware 2.0.0 that name is **not** in `/printer/gcode/help`; the
  printer defines `INNER_PREEXTRUDE_FILAMENT` (see section 5). How the call is
  resolved during a print: TO VERIFY ON HARDWARE. `;LAYER_CHANGE` marks layers.
- `print_sequence = by object` is refused with "<object> is too close to
  others, and collisions may be caused" / "is too tall" when clearance is
  short; the reason is in the log, exit code 0xFFFFFFC1.
- The prime tower's default position (X 31, Y 214.5 on the U1 presets) can
  hit an object: "gcode path conflicts found between WipeTower and <object>",
  exit 0xFFFFFF9B. `wipe_tower_x` / `wipe_tower_y` (not in the presets) can be
  set in the process JSON and show up in the config block.
- Exported project opened in the GUI (01.10.01.50): `Application
  Snapmaker_Orca-01.10.01.50`, one plate, `project_settings.config` built
  from the flattened presets -> printer Snapmaker U1, 4 x Generic PLA with the
  head colours, painted Spider-Man in white/black on T0/T1, support enforcers
  kept, prime tower shown. The app showed its "2.4.1 available" dialog first.

Not yet tested: `--export-slicedata`, opening a file in an already-running
Snapmaker Orca instance (the test started a new one), per-layer colour changes
(`custom_gcode_per_print_z.xml` is dropped with a note), PrusaSlicer painting
(`slic3rpe:mmu_segmentation`, not read), loading the exported project back
into the CLI (it has plates, so it would crash on 01.10.01.50).

## 3. `Snapmaker_Orca.conf` structure (read 2026-10-28, 01.10.01.50)

- JSON object followed by one trailer line `# MD5 checksum <hex>`; the file is
  not plain JSON, so parse the leading object and ignore the trailer. What the
  checksum covers is unknown (we never write the file, so it does not matter).
- `app.version` = `01.10.01.50`, `app.curr_bed_type` = `"4"`, `header` =
  `Snapmaker Orca 2.4.0`.
- `presets.machine` = the selected machine (`Snapmaker U1 (0.4 nozzle)`);
  `presets.filaments` was `null`.
- `orca_presets` = list, one entry per machine the user has used, with keys
  `machine`, `process`, `filament`, `filament_01`, `filament_02`, `filament_03`,
  `filament_colors` (`#FFFFFF,#000000,#F4E2C1,#ED1C24`), `filament_colour_mode`,
  `filament_multi_colors`, `flush_volumes_matrix` (16 `|`-separated numbers,
  zero diagonal → 4×4), `flush_volumes_vector`, `curr_bed_type`.
- Four colours and `filament` + `filament_01..03` → `filament` is T0 and
  `filament_NN` is T<NN>. Matrix orientation (row = from tool, column = to
  tool, row-major, mm³) follows upstream OrcaSlicer and is `TO VERIFY IN
  SNAPMAKER ORCA`. The real values support it: black→white (`[1][0]` = 703)
  is far larger than white→black (`[0][1]` = 223). The meaning of
  `curr_bed_type` numbers is not verified, so only the raw value is reported.
- Personal data in the file: `download_path`, `last_backup_path` (user name),
  `slicer_uuid`. The test fixture leaves them out.

## 4. Installed Windows 2.4.1 recheck (2026-10-28)

The 0.08 mm Spider-Man comparisons predate the painting-remapping fix and are
not valid. The 4h 42m / 79.9 g / 353-change baseline is from **01.10.01.50,
0.20mm Standard, after the fix**; do not relabel it as a 2.4.1 measurement.

Reproducer: `python research/m4-probe/recheck_release.py <fresh work directory>`.
It copies the installed vendor presets into the work directory and keeps each
probe's exact command, settings, log and output. The committed
`research/m4-probe/recheck-2.4.1.json` holds the measured summary; local evidence
is under `runs/recheck241-complete/` (ignored). No printer calls were made.

- **Preset location regression fixed in Print Copilot:** after the update,
  `%APPDATA%/Snapmaker_Orca` has config and `user/`, but no `system/`. The bundled
  profiles are at `C:/Program Files/Snapmaker_Orca/resources/profiles/`.
  CLI and MCP now use that directory from the selected executable when the
  legacy `system/` directory is absent, keeping user inheritance and config
  reads in the original user directory. No installation or user preset writes.
- Bundled process **`0.20mm High Quality @Snapmaker U1 (0.4 nozzle)`** replaces
  the old Standard name in this installation. Missing names still fail; there
  is no product alias or silent preset substitution. Integration tests select
  one of the two explicitly named reference processes available in the install.
- **Still crashes (0xC0000005):** direct inherited system presets,
  `wipe_tower_filament="0"`, and `--export-3mf`. Export writes G-code first,
  then crashes without producing a 3MF; that remains a failed run.
- **Input requirements and corrections:** Windows paths (`/c/...` is refused)
  and explicit colors for the painting probe. A machine marked `from=User`
  works when its system `inherits` reference is preserved; the earlier claim
  that `from=system` is always required was incorrect. Four filament presets
  were used throughout. A white cube with its bottom painted black uses T0/T1
  and has 3 changes with colors; without them it uses only T0 with 0 changes.
- **Enum/logging and help corrections (2026-10-29):** invalid `support_type`
  becomes `normal(auto)` with exit 0, but `--debug 4` logs the substitution
  at info level. `--help` prints the option list in a real Windows console;
  our redirected-output capture missed the reopened `CONOUT$` streams.
  The original missing-help and wholly-silent-substitution claims are withdrawn.
- **Output path observation:** directory length 229 works and 230 fails for
  the tested generated filename on this Windows installation. Do not treat
  that threshold as a universal directory limit or a confirmed root cause.
- **Plate-only crash fixed:** adding a `<plate>` section to the prepared copy
  succeeds with identical measurements (3915 s, 19.61 g, 108 changes).
  A synthetic copy with `Application=Snapmaker_Orca-2.4.1` but no project
  settings or plates still crashes. This is a robustness case involving
  incomplete metadata, not proof that ordinary GUI-saved projects fail.
- **Generated-project/tower audit (2026-10-29):** the original generator writes
  `version` as a JSON array where the project loader expects a string, causing
  a config parse error. After correcting it to the string `2.4.1.0`, the
  project loads without that error, but four differently colored filament
  configurations sharing the same preset name still disable the tower.
  Changing only the names to distinct values preserves it (both controls exit
  0 with one G-code, effective `enable_prime_tower` 0 versus 1, the same four
  colors). Separately, explicit `--filament-colour` values also preserve it in
  the original probe. Info/warning logs explain the single-filament mapping
  decision. The historical 2039 s / 7.78 g versus 3915 s / 19.61 g measurements
  are from the original probes, not these corrected controls. Keep the current
  slicing-copy workaround; this audit does not establish that all generated
  projects lose their tower or fix the project's generator.

  Corrected source context: [console help](https://github.com/Snapmaker/OrcaSlicer/blob/v2.4.1/src/Snapmaker_Orca.cpp#L6160),
  [User preset identity](https://github.com/Snapmaker/OrcaSlicer/blob/v2.4.1/src/Snapmaker_Orca.cpp#L1780),
  [substitution logging](https://github.com/Snapmaker/OrcaSlicer/blob/v2.4.1/src/Snapmaker_Orca.cpp#L1745),
  and [filament-name deduplication](https://github.com/Snapmaker/OrcaSlicer/blob/v2.4.1/src/Snapmaker_Orca.cpp#L1937).
  Local commands and raw logs are retained under `runs/issue-audit-20261029/`
  and `runs/issue-correction-check/`; the corrected tower reproducer is also
  included in [#1119](https://github.com/Snapmaker/OrcaSlicer/issues/1119).
- **Purge matrix remains ineffective on this U1 probe:** all-zero and all-500
  matrices produce identical 3915 s / 19.61 g / 108 changes. `prime_volume=5`
  instead of the bundled 45 gives 3165 s / 13.35 g; tower disabled gives
  2039 s / 7.78 g. These are slicer measurements, not physical print quality
  or firmware pre-extrusion measurements.
- Sequential printing still refuses insufficient clearance (synthetic tower:
  "too close to others", exit 0xFFFFFFC1). NX-01 plate 4 no longer reproduces
  the old default tower collision with these bundled presets; it slices with
  a tower without relocation. The controlled collision/retry unit test remains.
- `--export-slicedata <output directory>` is accepted and writes normal G-code,
  but this invocation produced no additional slice-data artifact. The feature's
  useful invocation/output remains unresolved.
- Real-project integration rerun: synthetic projects, Spider-Man, NX-01,
  Marge colour reduction and Majora's Mask strategy comparison. Downloaded
  model archives remain ignored for licensing. Final verification: **218 tests
  passed**, none skipped; ruff lint and format checks passed.
  Spider-Man at **0.20mm High Quality, Generic PLA x4, fixed test head colours**: **19475 s (5h 24m 35s),
  79.24 g, 353 changes**, tower enabled. Different release and process from the
  historical 4h 42m result; do not use the pair as a like-for-like benchmark.

- **`wall_generator` override (checked 2026-10-29):** `arachne` (a value used
  by profiles shipped in `resources/profiles/*/process`; the U1 presets use
  `classic`) passed as a process override reaches the G-code config block
  (`wall_generator = arachne`) and changes the toolpaths: on a 20 mm wide,
  0.6 mm thick fin at 0.20mm Standard, the fin layers extrude 95.6 mm of
  filament as outer wall with `classic` and 69.4 mm with `arachne` (the fin's
  volume is about 80 mm). Slicer toolpaths only; no physical print.
- **`brim_type` (checked 2026-10-29):** the U1 process presets leave the key
  out and the config block shows the slicer default `auto_brim`. Passed as an
  override (`no_brim`, `outer_only`) it reaches the config block and the
  `;TYPE:Brim` toolpaths follow it, also in an exported project sliced as a
  whole. `auto_brim` added a brim to a 5 x 5 x 60 mm pillar (15.5 mm of
  filament) but none to a 20 mm cube or to a 100 mm figure standing on
  335 mm2; `outer_only` on that figure: 45.8 mm, 3472 -> 3512 s,
  12.22 -> 12.36 g (slicer figures).
- **Object settings beat process overrides (checked 2026-10-29):** in a
  two-cube project where one object sets `sparse_infill_density = 80%`,
  overriding the process to 5% cut the sparse infill by 519 mm without the
  object setting but only by 262 mm with it: the object kept its 80%. The
  config block shows only the process value. Likewise a MakerWorld figure with
  `enable_support = 1` on the object prints supports while the config block
  says `enable_support = 0`.
- **GUI project load resets unlisted keys (2.4.1, checked 2026-10-29):** when
  the app opens a 3MF, [`load_external_preset`](https://github.com/Snapmaker/OrcaSlicer/blob/v2.4.1/src/libslic3r/Preset.cpp)
  sets every key not named in that preset's `different_settings_to_system`
  entry (process, filaments..., machine; keys joined by `;`) back to the
  named preset's value. Separately, a `version` stored as a JSON array makes
  the GUI log `type must be string, but is array` and skip the keys sorted
  after it (`wall_loops`). A generated project with both defects opened with
  2 walls / 15% although it stored 4 / 25% (GUI slice 96.20 g versus 113.11 g
  from the CLI, which keeps the stored values). With the changed keys listed
  and `version` a string, the GUI shows 4 / 25% and its own slice measures
  113.11 g, 3 h 33 min 55 s, equal to the CLI.

Still open: 2.4.1 GUI round-trip/launch into an already-running instance,
per-layer colour changes, PrusaSlicer painting, layer-height ranges, hardware
pre-extrusion and print quality without the tower. The old 0.08 mm comparison
has intentionally not been republished or treated as valid; remeasure it if needed.

## 5. U1 printer API (verified 2026-10-28, firmware 2.0.0)

- mDNS: the U1 answers a PTR query for `_snapmaker._tcp.local` (it is the only
  service it lists under `_services._dns-sd._udp.local`). TXT records:
  `machine_type=Snapmaker U1`, `device_name=U1`, `version=2.0.0`,
  `ip=<current address>`, `link_mode`, `region`, plus `sn` and `userid`
  (never stored or returned). `printer/discovery.py` uses this; `lava.local`
  (the Klipper hostname) does not resolve on Windows.
- Moonraker 2.0.0, API 1.4.0, answers on **port 80 and port 7125** (same
  instance). `/access/info`: `login_required: false`, `trusted: true`; no API
  key is needed on the LAN.
- `/machine/system_info` `product_info`: `machine_type: "Snapmaker U1"`,
  `device_name`, `nozzle_diameter` per head, `firmware_version`. It also has
  serial numbers: never copy them into the repository.
- Components include `file_manager`, `job_queue` (paused, empty), `history`,
  `webcam`, `octoprint_compat`, `snapmakercloud`, `mqtt`.
- Objects: `extruder`, `extruder1`..`extruder3` with `temperature`, `target`,
  `state` (`ACTIVATE` on the carriage, `PARKED`), `nozzle_diameter`,
  `extruder_offset`, `switch_count`; `toolhead.extruder` names the active head.
  Per-head `filament_motion_sensor eN_filament` and
  `filament_entangle_detect eN_filament`; `filament_feed left|right`.
- `filament_detect.info` is a 4-entry list of RFID tag data (`VENDOR`,
  `MANUFACTURER`, `MAIN_TYPE`, `SUB_TYPE`, `RGB_1`, hotend/bed temperatures,
  `OFFICIAL`, `CARD_UID`); entries without a tag read `NONE`. Entry i is head
  T<i> (verified 2026-10-28: the black spool read on entry 1 printed from T1).
- `/server/files/metadata` for Snapmaker Orca G-code includes per-head lists:
  `filament_type`, `filament_colour`, `filament_weight`, `filament_used_mm`,
  `nozzle_diameter_list`, `nozzle_temp`, plus `estimated_time`,
  `filament_weight_total`, `slicer` (`SnapmakerOrca`).
- `/printer/gcode/help` lists `CANCEL_PRINT` (wrapping `CANCEL_PRINT_BASE`),
  `TURN_OFF_HEATERS`, `PAUSE`/`RESUME`, `SDCARD_PRINT_FILE`, `PRINT_START`,
  nine `SM_PRINT_*` macros (`CHECK_SWITCH_EXTRUDER`, `EXTRUDER_PREHEAT`,
  `AUTO_FEED`, `END_AUTO_UNLOAD_FILAMENT`, `START_LINE`,
  `START_LINE_EXTRUDER_0..3`) and `INNER_PREEXTRUDE_FILAMENT`, but not
  `SM_PRINT_PREEXTRUDE_FILAMENT`.
- `INNER_PREEXTRUDE_FILAMENT` (from `configfile.settings`): moves to the
  discard position, heats (`TEMP` default 220), extrudes `LENGTH` default
  **20 mm** at `SPEED` default F360 (10 mm at F120 with `SOFT`), retracts
  0.5 mm, cools 5 s, cuts and cleans the nozzle. Whether every tool change
  runs it, and with which length: TO VERIFY ON HARDWARE.
- Upload (`POST /server/files/upload`) verified 2026-10-28: a 3.9 MB G-code
  landed in `gcodes`; the reply is NOT wrapped in `result` (it is
  `{"item": ..., "action": ...}` directly, as Moonraker documents).
- Bundled 2.4.1 presets may start with a UTF-8 BOM (`0.20mm Standard @Snapmaker
  U1 (0.4 nozzle).json`, `fdm_process_common.json`); read them as `utf-8-sig`.
- Start (`POST /printer/print/start?filename=...`) verified 2026-10-28: the
  standard request is enough; `print_stats` went to `printing` and the T1
  heater targeted 140 C (start G-code preheat) with the bed at 60 C.
  First real print (dishwasher salt funnel, black PLA SnapSpeed on T1,
  0.20mm Standard, no overrides): `complete` in 1881 s against 1912 s
  estimated. Part fine; one visible line on the cone and the tube is the
  aligned seam (`seam_position = aligned`, all wall starts at the same
  angle in the preview). The mesh is fine (~148 segments per circle), so
  facets do not explain the faint vertical lines; not diagnosed.
- Second real print (a MakerWorld project, 2026-10-28): it was sliced
  with a layer height other than the one the project was saved with and
  infill and supports were misreported, because MakerWorld 3MFs set infill and
  supports on objects and parts, which the G-code header does not show.
  Inspect, slice and export now list object/part settings and the
